## 1. 一个判断：第二个平台是这一阶段的分水岭

`app/providers/registry.py` 那层设计得好，加平台**确实只改一个文件**。
但前端这一轮所有口径都建立在「只有一个平台」这个隐含假设上，
第二个平台一接就会同时引爆四件事：

1. **「提及率 60%」跨平台是什么意思？**
   DeepSeek 80% + 豆包 20% 混算出 50%，对运营没有任何操作价值 ——
   他要知道的是「豆包上我不行」。`/v1/counts` 早就支持 `group_by=platform`，
   但前端一次都没用过。
2. **命中矩阵要变形。** 现在是 提问 × 品牌。加一维就是三维，而三维矩阵不可读 ——
   所以大概率结论是「平台是筛选器，不是维度」。这个决定影响 A6 整页版式。
3. **`apps/web/README.md` §5「平台环形图不做」的理由当场失效**
   （原因写的是「只有一个平台，画出来是假装有多样性」）。
4. **job 数翻倍**，`services/counts.py` 那个「拉 `full_text` 进 Python 再累加」
   的债会提前咬人。

还有一条容易漏的：**每个平台一份会过期的登录态。**
DeepSeek 用 `storage_state`。过期的表现是一批 job 全 `failed` ——
而这和「平台没接」「网络问题」的排查方向完全不同，现在没有任何东西能区分它们。

**所以顺序是：先定口径，再写 Provider。** 反过来做，Provider 写完前端也接不上。

### 1.1 还有一个更靠前的前提：采集出口的地理位置

**已确认：出口 IP 会影响 AI 的回答。** 而 VPS 在新加坡（机房 IP），
服务对象是大陆用户，接下来要接的三个平台（豆包 · 千问 · Kimi）**全是大陆服务**。

两个后果，都很硬：

1. **数据口径本身就不对。** 从新加坡采到的回答不代表大陆用户看到的回答。
2. **调试时会有两个变量同时在动。** 从机房 IP 开发大陆平台的 Provider，
   抓失败时分不清是「Provider 写错了」还是「IP 被风控了」——
   而这两个的排查方向完全相反。这个问题会贯穿三个平台。

**所以采集出口迁移排在接平台之前**，见 §3「零、采集出口与部署拓扑」。

**⚠️ 迁移会造成基线断点。** run 27 / 54 与迁移之后的 run **不可比**。
迁移后第一次 run 的 `run.note` 必须写明「采集出口已迁至大陆」，
且 `P2-31` 趋势图要能表达这个断点 —— 一条跨越迁移点的折线画成连续的就是骗人。

#### P2-01 的收成：冒烟第一次跑就抓到一个已上线的 bug

`first_offset` 是 Python 的**码点**索引，而前端用 `String.slice` 按 **UTF-16
单元**切 —— 一个 🏃 在 Python 里算 1、在 JS 里算 2。含 emoji 的回答（DeepSeek
很常见）证据页高亮全部错位。

**线上没有画错** —— `buildHighlights` 那条自检拦住了：对不上就不画、改报告警。
但代价是那些回答一律没有高亮。修法见 `apps/web/src/lib/l3/text.ts`；
顺藤还摸到同类第二处（`isPreviewTruncated` 拿码点数比 UTF-16 长度）。

**`docs/API.md` §7.1 那条不变量的写法本身就是错的**（写成了
`full_text.slice(...)`），它正是误导的源头，已更正为分别给出 Python 与 JS 两种写法。

这条记在这里，是因为它回答了「为什么冒烟值得先做」——
它抓的不是「按钮点不动」，是**跨语言口径分叉**这种任何单层测试都看不见的东西。

#### P2-02 顺带补的后端一致性

做任务编辑时发现 **`start_run` 不检查 `task.is_active`** —— 「已停用」只是任务
列表里的一个徽章，而 `create_run` **是**按 `Prompt.is_active` 过滤提问词的。
同一个字段名一处当真、一处装饰。

之前不明显，因为界面上从没有停用任务的入口。编辑入口一做出来，
不补这条就等于在界面上写一句假话。已补：停用的任务发起运行返回 400
（不是 404 —— 任务确实存在、你也看得见，只是它被停用了）。

#### ⚠️ 豆包这条路可能不成立（2026-08-15 实测）

**接豆包不是「把 DeepSeek 的选择器换一套」，风险级别不一样。**

第一条探针提问发出后，页面直接跳 `?from_logout=1`，登录态当场失效。
在采集节点容器里实测，crawler 的浏览器有四个明着写着「我是自动化」的破绽
（`webdriver=True` · `plugins=0` · `window.chrome=undefined` · UA 里带
`HeadlessChrome`）。豆包同时加载了 `s2-security-audit` / `-verify` / `-message`
三个模块 —— 它在**主动做检测**，而 DeepSeek 一年没咬过我们。

已做的加固见 `BACKEND.md` §7.5（新 headless + 参数 + UA + persistent context），
节点实测四项全过。**但这只说明今天能过。**

| | DeepSeek | 豆包 |
|---|---|---|
| 反自动化 | 一年没遇到 | **未加固时发一条就登出** |
| 答案气泡 | `.ds-markdown` | `.md-box-root` + `[data-message-id]` |
| **完成判定** | 长度连续不变轮询 | **`[data-streaming]` / `data-complete` 状态位** |
| 输入框 | `textarea` | `textarea` 有两个，**第二个是 `aria-hidden` 的隐藏替身** |
| 首页 / 输入区 | 语义类名 | 生成式工具类，只能靠 `aria-label` + `placeholder` |

> **一处更正（同日）**：最初判断「豆包无 `data-testid`，只有生成式工具类」——
> 那是**首页与输入区**的情况。**对话区有完整的 `data-*` 体系**（48 个属性名），
> 答案气泡的 `md-box-root` 是稳定语义类。**这一点上豆包不比 DeepSeek 脆，
> 完成判定甚至更好。**留着那个夸大的判断会让下一个人高估工作量。

**两条仍然成立的判断：**

1. **反自动化是一场会持续的对抗。** 加固之后今天能过（实测：persistent +
   新 headless + UA + 参数，发提问不再登出），但不代表下个月能过。
   每次失效的表现都是「一批 job 全 failed」——
   P2-08 会归成 `parse_error`（不重试，分类是对的），但看不出根因。
2. **如果某次改版之后长期过不去，那时要重新讨论的是「豆包还做不做」，
   不是「再加一层伪装」** —— 本仓不做 stealth 注入，
   理由见 `providers/browser.py` 的模块 docstring。

**为什么把 P2-07 也提到豆包之前**（2026-08-15 改的顺序，原计划它依赖 P2-06a）：

一份**过期 11 天**的登录态悄悄让每次 run 丢掉头几条，而没有任何地方报警 ——
这正是 P2-07 要防的东西，它刚刚真实发生了一次，代价是三天的数据口径不对
（§3「零」）。而**接豆包会再多一份会悄悄过期的凭证**：先接平台再做健康度，
等于把同一个坑再挖一个。

现在还多了一个具体抓手：**WAF cookie 的类型能直接暴露「这份登录态是从哪儿建的」**
（`aws-waf-token` = 境外，`HWWAFSES*` = 境内）。这比原计划的
「上次成功抓取距今多久」信息量大得多 —— 后者只能发现「全红了」，
而这次的故障形态是**没全红，只是悄悄降级**。

**为什么把 P2-35 与 P2-16 提到豆包之前**：它们都会**污染豆包的调试**。
记不上口径 + 每次 run 莫名丢头几条，会让「豆包 Provider 到底写对没有」
这件事更难判断 —— 而调试时不能有多个变量同时在动，这也是迁移排在
接平台之前的同一条理由。

**P2-33 是临时方案，退役条件写死：接完豆包（P2-06a）就做 P2-34。**
不设条件它会永远留着 —— 而它带着两个不该长期存在的代价（数据库凭证跑在
家宽链路上、截图降级）。

#### 第一次真抓：run 294（2026-08-16）—— provider 成立，但挖出两个 bug

**结论先写：豆包 provider 是能用的。** 6 条 `ok`，1000–1700 字，
内容质量高（安踏 / 李宁 / 特步 / 361° / 乔丹，带价位与适用人群）。
**选择器、指纹加固、SSE 拦截都被证明是对的** —— 这一点不用再怀疑。

预定要盯的三处，结果：

| 看什么 | 结果 |
|---|---|
| `failure_kind` 是不是 `login_required` | **不是，一条失败都没有** —— 而这本身就是 bug A |
| `raw_json.session_deleted` | **全是 `false`** —— 见 bug B |
| `environments[]` | ✅ 19/20 打上同一环境 `changsha-home\|120.228.64.174\|Asia/Shanghai\|real\|cn\|huawei`，单一出口。未打标的 1 条是从没被领取的 pending。**P2-36 工作正常** |

**bug A（已修，commit `b6c4b56`）· 超时被伪装成成功。**
`_wait_for_answer` 超时后 `return prev`，而豆包不答时 `.md-box-root`
匹配到的是**用户自己那条提问气泡** —— 于是 11/17 条以「成功，答案 = 提问原文」
入库（`full_text` 11–16 字符，latency 全是 126 秒）。
靠 L1 的 `too_short` 才被发现，**但那是运气**：提问词长过阈值就会当成真答案。
已改成抛 `DoubaoAnswerTimeout(TimeoutError)` → `failure_kinds` 按类型归 `timeout`
→ P2-16 退避重排。

**bug B（未修）· 会话删除从来没成功过。**
`page.url` 一直停在 `https://www.doubao.com/chat/local_XXXX`，`local_` 是客户端
占位符，所以 `_delete_current_session` 每次都走「拿不到会话 id」分支返回 False。
**账号里每抓一条就堆一个对话，一条没删。** 这可能正是现象 C 的原因之一 ——
所以先别急着单独修它，等 C 定性。

**现象 C · 豆包在第 3 个提问词、第 6 条之后就不答了。**
前 6 条 35–47 秒正常，之后 10 条全部打满 120 秒。
**这就是为什么 A 必须先修** —— 失败全被伪装成成功时，重试机制根本不触发，
也就拿不到「退避之后还会不会失败」这个唯一能区分限流与封禁的信号。

**A 修完当天就拿到了第一组数据（job 532）**：修复上线后那条残留 job
连试 3 次（03:20 / 03:21 / 03:23，中间还隔了停机的约 20 分钟），
**三次全部超时**，每次都是同一句：

```
等答案超过 120000ms；页面上最长气泡 12 字符（还在 streaming=True）
```

三条推论：

1. **不是短时限流。** 跨越约半小时、四次尝试，一次都没恢复。
   限流该在这个尺度上放行。
2. **豆包收下了消息但永不给答案** —— `streaming=True` 一直在。
   不是拒答、不是报错，是**假装在生成**。这是典型的静默封锁形态。
3. **「最长气泡 12 字符」= 提问的长度**，直接印证了下面那条被证伪的判断。

**第二组数据（run 295，同日下午）把三个解释一次排除了。**
换了新 `storage_state` + 手工清空全部历史会话 + 隔了时间，**照样复现**，
而且配额从 6 条掉到 3 条：

| 曾经的解释 | 判定 |
|---|---|
| 短时限流 | ✗ 跨小时、跨会话都复现 |
| `storage_state` 降级 | ✗ 换新的之后撑得更短（6 → 3） |
| bug B 的会话堆积 | ✗ 清空之后照样复现 |

**「降速」这条预案也被证伪了。** `BACKEND.md` §7.2 第 4 条写着「大面积限流时
要的是全局降速/熔断」—— run 295 每条间隔 5–7 分钟，比 run 294 成功那 6 条的
**0.9 分钟慢了六七倍，结果反而更差**。所以这不是"单位时间请求太密"，
那条预案对这个对手不成立。惩罚是**按账号跨会话累积**的。

#### 外部情报（2026-08-16，经 Grok 实时检索）

社区材料**独立印证了两条我们自己推出来的判断**：

1. **持久化 profile 是已验证的做法。** `doubao2api` 有 `DOUBAO_BROWSER_DATA`
   配置，目的写明是「复用 `webid` / `device_id` / `msToken`，避免每次冷启动
   换指纹」—— 和我们从「老会话 + 空白设备自相矛盾」推出的结论一致。
2. **stealth 注入对豆包无效。** `lza6/doubao-2api` 标配 Playwright stealth，
   仍然中人机（#5）、签名超时（#7）；Linux.do 2026-05 有人用 Playwright MCP，
   结论是「效果更不佳，而且慢」。**本仓「不做 stealth 注入」那条原则，
   在这个对手身上不只是洁癖，是它确实不管用。**

另外三条值得记：

- 豆包**公开已知**的防线是 `a_bogus` 签名 + `msToken`(BDMS/Slardar) +

#### 登录态是带地理位置的（2026-08-15，代价最大的一条）

`storage_state` **不只是「登录了没有」，它记录着「你是从哪儿登的」。**
迁移时我们把 VPS（新加坡）导出的那份直接拷到大陆节点用了三天。两份会话一对比：

| | 新加坡导出 | 长沙导出 |
|---|---|---|
| WAF cookie | `aws-waf-token`（**AWS WAF**，且**已过期 11 天**） | `HWWAFSESID` / `HWWAFSESTIME`（**华为云 WAF**） |
| `searchEnabled` | `true` | `false` |

**DeepSeek 的境内与境外流量走的是两套不同的基础设施。** 我们一直拿着一张
AWS 的、而且过期了的门票去敲华为云的门 —— 每次 run 头几条卡在 WAF 挑战上。

同时发现第二处「切了 IP 没切环境」：**浏览器上报的时区一直是 UTC**。
`DeepSeekWebProvider` 只设了 `locale="zh-CN"`，从没设 `timezone_id`，
Playwright 就取了容器的系统时区。于是服务端看到的是
**「IP 在长沙、语言中文、时区在伦敦」**。

两处一起修之后（`CRAWL_TIMEZONE_ID` + 在大陆重建登录态）：

| run | 样本 | 失败 | 国际/大陆 提及比 |
|---|---|---|---|
| 215 | 10 | 2 | 0.96 |
| 292 | 9 | 1 | 1.64 |
| **293** | **20** | **0** | **1.19** |

**三条结论：**

1. **「迁移出口」不等于「改 IP」。** 至少还有：浏览器指纹（时区/语言）、
   登录态的签发地、以及服务端按签发地下发的功能开关与模型通道。
   **只验 IP 就宣布迁移完成是不够的** —— `deploy.sh verify` 当时四项全过。
2. **重建登录态必须从目标出口做。** 办法见
   `scripts/export_storage_state.py`：开一条到采集节点的 SOCKS 隧道
   （`ssh -o ExitOnForwardFailure=yes -D 18080 -N -f`），
   `--proxy socks5://127.0.0.1:18080`。脚本会在登录**之前**打印出口 IP。
3. **品牌构成 1.64 → 1.19 但没回到 0.96，且样本数不同，不足以下结论。**
   P2-32 那个「出口影响回答」的结论本身也建立在 n=10 的目视对比上 ——
   要坐实它需要 P2-36（把采集环境记进数据）之后再做一次对照。

#### 这次踩出来、必须固化的操作经验

| 事 | 结论 |
|---|---|
| **镜像别从 mcr 拉** | 家宽直连 136KB/s、走代理 386KB/s → 2GB 要 **90 分钟**。**从 VPS `docker save` 经 tailnet 传只要 66 秒**（21MB/s） |
| **代理：build 走，run 绝不走** | 家里云上 mihomo 在 7890。走代理出口变成香港 `42.200.231.233`，直连才是 `36.157.231.164`（长沙移动）。**crawler 容器不设任何 proxy 环境变量** |
| **postgres 不改绑定** | 仍只绑 `127.0.0.1:5433`，靠 `tailscale serve --tcp 5433` 暴露给 tailnet。公网已验证连不上。**别为了省事改成 `0.0.0.0`** |
| **家里云不是空闲机器** | 上面跑着 tradepod（带 API key）· mihomo · jellyfin · qbittorrent。**任何 `pkill`/`pgrep` 都要按精确 PID**，模式匹配会误伤 |
| **部署会把冷备静默拉起来**（2026-08-14 发现并修） | 旧判断是「容器存在就 `compose up -d`」，而 `docker ps -a` **连已停止的容器一起匹配** —— 于是每推一次代码就把 VPS 那台冷备 crawler 启用一次，而没有任何地方会报错。P2-35 那次部署实际让它跑了 4 小时（碰巧没人发起 run 才没污染）。已修：`deploy/deploy.sh` 对停止态走 `compose create --build`（重建但不启动）。**教训是通用的：靠一条手动 `docker stop` 维持的纪律，会被自动化流程无声撤销** |
| **部署 hook 曾在执行中改写自己**（2026-08-14 修） | 旧 hook 在 `cp` 覆盖 `$GIT_DIR/hooks/post-receive` 之后继续执行，而 bash 按字节偏移续读 —— 沙箱复现证实：**`docker compose up` 与全部健康探测整段被跳过，`git push` 照样报成功**。已拆成「存根 + `deploy/deploy.sh` 正文」，正在执行的文件永不被改写；另加 `flock` 防并发 push 在上一次跑到一半时覆盖 `deploy.sh`。见 `BACKEND.md` §10.2 |

#### 领取的原子性：已核实，比文档写的好

`services/crawl_jobs.claim_pending_jobs` 的 docstring 写着
「simple, single-worker safe enough for demo」——**这句低估了实现**：

```python
select(CrawlJob).where(status == "pending").with_for_update(skip_locked=True)
```

`FOR UPDATE SKIP LOCKED` **本来就是多 worker 安全的**，配合 600 秒的僵死回收
（`running` 超时 → `failed`，刻意不回 `pending`，理由见那个函数的 docstring），
机制是完整的。**P2-34 的 lease 直接沿用这个模式即可，不必另造。**

#### 但备份链路只能冷备，不能热备

技术上两个 crawler 可以并行且不抢同一条 job。**但那样一次 run 的样本会同时
来自新加坡和大陆两个出口** —— 而迁移的全部理由就是出口影响回答。

更隐蔽的是：**数据里没有任何字段记录某条样本是哪台机器采的**（P2-36），
混了就分不开、事后也查不出来。这比「口径变化混进表现变化」还深一层。

**所以 VPS 那台 crawler 是冷备**：平时停着（`docker stop geo-crawler`），
家里云挂了才启（`docker start geo-crawler`）。**启之前必须意识到：
从那一刻起采集出口换回了新加坡**，那段数据与前后不可比。

**隧道期间截图怎么办：暂时关掉**（`SCREENSHOT_DIR` 置空）。证据页那个「查看截图」
按钮本来就是条件渲染的，没有 `screenshot_path` 就不显示 —— **降级是干净的，
不会出现 404**。并在 `run.note` 里写明「这次运行未采集截图」。

**P2-34 有一个必须做对的细节：lease 的原子性。** 两个 worker 同时领任务不能领到
同一个 job —— 要用 `UPDATE ... WHERE status='pending' ... RETURNING` 单条 SQL 占位，
不是「先 SELECT 再 UPDATE」。且 lease 要有到期时间：worker 领了任务然后家里断电，
那批 job 不能永远卡在 `running`（现有的 `CRAWL_STUCK_JOB_SEC` 就是干这个的，直接复用）。

## 4. 产品决策

### 4.0 已拍板：多平台口径（P2-05）

**结论：平台是筛选器；「全部平台」这一档保留混算的总数，但把分母的构成摊开。**

推导的地基是一条区分 —— **取决于那块东西是用来诊断还是用来行动的**：

| | 用途 | 跨平台怎么办 |
|---|---|---|
| 提及率 / 首位提及率 KPI | 诊断 | **必须能分平台**。混出来的 50% 没有操作价值，运营要知道的是「豆包上我不行」 |
| 命中矩阵 | 诊断 | **强制单平台**。加一维就是三维，而三维矩阵不可读 |
| **覆盖缺口清单** | **行动** | **跨平台合计** |

缺口清单跨平台合计的理由：它的产出是「去哪些提问下**补内容**」，而 GEO 的机制是
内容在互联网上、AI 去读它 —— **补内容这个动作是平台无关的**，你不会为豆包单独
写一篇文章。而且合计之后样本翻倍，判级更稳：分平台时 n=3，**一个样本 = 33 个
百分点**，缺口判级会随机跳。

四条落地：

1. **KPI 的分母行在多平台时展开成构成**（`35 = DeepSeek 30 + 豆包 5`）。
   这是 §3.1「凡显示比率必须同时显示 m/n」的自然延伸 —— 单平台时 `21/35` 够了，
   多平台时不够，因为构成才决定这个数的含义。
2. **新增「分平台表现」面板**，一根 emphasis 条 per 平台。数据源
   `counts?group_by=platform`，**一次请求**。它直接回答多平台带来的唯一新信息。
3. **命中矩阵强制单平台**，上方带平台按钮，默认第一个。
4. **缺口清单保持跨平台合计**，副标题里说明。

**为什么留混算的总数**：客户会问「我在 AI 里的可见度是多少」，给不出总数的报告
在商业上是残缺的。**为什么必须摊开构成**：那个数会自己动 —— 两个平台表现完全
没变，豆包挂掉一半（`30+30 → 30+15`）就能让总数从 50% 涨到 60%。摊开构成之后，
任何人一眼看出「分母的构成变了，不是表现变了」。

### 4.0.1 已拍板：生产采集必须开联网搜索（P2-37）

**2026-08-15 拍板：客户不认不联网的结果，所以生产抓取必须开联网。**
这条原先挂在 §4.1「开联网搜索重抓」，现在方向定了，**但执行单列成 P2-37**
（理由：一次只动一个变量，见下）。

连锁后果四层，按咬人顺序：

1. **DeepSeek 也必须开。** 否则豆包有引用、DS 没有 —— 两个平台的证据页
   长得不一样，而 §4.0 刚拍板「平台是筛选器、总数混算」。
   混算一个「有引用」和一个「没引用」的池子，解释不了。
2. **开了 = 现有基线全部作废。** §6.3 那 35 条安踏（60.0%）是**不联网**条件下
   测的（`BACKEND.md` §7.0 明写「联网会改变回答内容分布」）。
   run 27 / 54 / 215 / 292 / 293 **全部降级成「历史（不联网）」**，要整套重抓。
3. **代码上还缺一步，不修的话开了也白开。** `_extract_citations`
   **只在非 SSE 分支里跑**，而两个平台都走 SSE（`BACKEND.md` §7.0 第 2 条）。
4. **连带**：P2-20（引用分析）从「被阻塞」变成可做；
   P2-31 趋势图要再画一条基线断点线。

**为什么不和 P2-06a 一起做**：那样豆包第一次真抓会同时带着「新 Provider」
与「联网」两个变量，且 DS 要在同一段时间重抓 —— 正是本仓一直在避免的局面。

> ⚠️ **豆包可能没有手动开关。** 2026-08-15 实测：输入区工具栏全是技能
> （PPT / 图像 / 写作 / 视频 / 翻译 / 录音 / 音乐），「快速」是**模型**选择器
> （快速 / 专家 / 工作任务 Turbo / Pro），**没看到联网开关** ——
> 大概率是它自动判断。若如此，「开没开」只能事后从回答里判断
> （`已阅读 N 个网页` 这类标志，`BACKEND.md` §7.0 用过这个方法），
> 而那意味着**联网与否不是我们能控制的变量**，P2-37 要先解决这个。

## 6. 回滚规范（迁移这段尤其要守）

`git push vps main` **就是上线** —— post-receive 直接 build 并重启，中间没有闸门。
迁移涉及部署拓扑变更，所以这段的回滚要提前想好。

### 三条规矩，按有效性排序

**1. 尽量「只加不改」。** 新增 compose profile、新增 worker 端点，
**旧路径保持能用**。这样回滚 = 停掉新容器，**根本不需要动代码**。
这是最有效的一条：**能不用 git 回滚的，就别依赖 git 回滚。**

**2. 数据库改动必须向后兼容。** P2-34 若要给 `crawl_jobs` 加 lease 字段，
**加可空列**，不改现有列 —— 这样隧道模式的旧 crawler 仍能工作，
两种模式可以并存过渡，而不是「切过去就回不来」。

**3. 迁移前打 tag。**

```bash
git tag p2-before-migration      # 已打，指向 4a0fd70（P2-04 收工）
```

出事时 `git revert` 有个明确的对照点，而不是去 log 里翻。

### 回滚动作

**不要 `push --force` 到部署仓** —— post-receive 会拿到一个 history 不一致的仓库。
用 revert：

```bash
git revert <bad-sha> && git push vps main    # 重新 build，几分钟
```

代价是重新构建。**所以真正的安全网是规矩 1** ——
让危险的东西活在容器编排层，而不是代码层。
