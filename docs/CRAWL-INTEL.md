## 0. 一句话现状（2026-08-17）

**三家都在阻断自动化，且手法一致：不报错、不弹验证码，只让某个功能静默失效。**

| 平台 | 强制登录 | 配额记在哪 | 当前状态 | **结构性可持续？** |
|---|---|---|---|---|
| **通义千问** | **否** | **当前匿名会话**（换 profile 即清零，**IP 不记账**） | ✅ 在产数据 | ✅ **可持续 —— 没有账号可被封** |
| 豆包 | 是 | 账号，跨会话累积 | ⏸ 暂缓 | ❌ 配额 6 → 3 → 1/5 单调衰减 |
| DeepSeek | 是 | 账号 | ⛔ 禁言至 2026-08-20 12:09 | ❌ ToS 有升级阶梯（见 §3.3） |

**最重要的一条判断**：三家的可持续性不是同一个量级，**不该用同一套采集架构**。

## 1. 软阻断的三种形态（全部实测）

| 平台 | 形态 | 日期 |
|---|---|---|
| 豆包 | 收下消息，**永远「正在生成」**（`[data-streaming]` 挂满 120 秒），从不给答案 | 2026-08-16 |
| 千问 | 文字打得进输入框，**回车不提交**，URL 不变，页面无任何提示 | 2026-08-16 |
| DeepSeek | 侧栏与历史全渲染，**输入区从未生成**（HTML 里连 `textarea` 字符串都没有） | 2026-08-17 |

### 1.1 两条方法论（比具体形态更值钱）

1. **功能静默失效时，先用手机端看一眼。**
   DeepSeek 那次在节点上挖了六轮 DOM，只能确认「输入区不存在」；
   而**手机端直接写着**「您的帳號已被禁言至 2026/8/20 12:09」。
   **桌面网页版藏原因，移动端露出来。**
2. **报错整齐一致 = 平台侧状态，不是我们的 bug。**
   20 条 DeepSeek job 全部卡在 **32 秒**（30s 选择器超时 + 2s 开销）。
   真正的限流/网络超时会有抖动。**这么整齐说明它是一个稳定状态。**

### 1.2 分类陷阱

这三种形态**都会被归成 `timeout`（可重试）**，而真相都是需要人工介入。
豆包 bug A 就是这么把「超时」写成「成功」的（详见 `PHASE2.md`）。
**分类器认不出的新形态，宁可归 `unknown` 也别归成可重试。**

## 2. 各平台的技术细节（实测）

### 2.1 通义千问（平台代码 `tongyi`，站点 `qianwen.com`）

> `tongyi.com` 只是 302 跳过来（`?ch=tongyi_redirect`），直接用落地页。
> 平台代码保持 `tongyi` 是有意的 —— 它在 `ALLOWED_PLATFORMS` 与历史数据里。

| | |
|---|---|
| 输入框 | `[contenteditable='true']`（Slate，`data-slate-editor`）。**页面上没有 `textarea`** |
| ⚠️ 交互 | **`click()` 会超时** —— 首屏大图（`absolute inset-0 h-[266px]`）盖在中心点上，另有 `z-[1001]` 浮层。**必须 `element.focus()` + 键盘输入** |
| 答案气泡 | `.answer-common-card`（干净）。`.chat-answers-card-wrap` 会把「N 篇来源」卷进来 |
| 提问气泡 | `.message-card-wrap.question`（与答案分离，**不会像豆包那样混淆**） |
| 完成判定 | **没有 `data-streaming` 等价物**。逐秒记录 60 秒，唯一带 stream/generat/loading 的属性是图片的 `loading=lazy` |
| 「停止回答」按钮 | `role=button name="停止回答"`。**只能当正向信号** —— 实测第 8 秒消失而正文长到第 15 秒 |
| 风控脚本 | 只有 `g.alicdn.com/secdev/sufei_data/3.9.14`（阿里全站通用设备 ID）+ `track.uc.cn` |
| 匿名配额 | **约 5 个对话**，之后发送静默失效。**换新 profile、同 IP 立刻清零** |
| 登录态下的边界 | **一次 run 内第 13 条起开始失败**（2026-08-21，两次复现）。**机制未知**，见下 |
| 典型耗时 | 27–42 秒 |

#### 「第 13 条」现象：复现了两次，但机制还没定性（2026-08-21）

按 `started_at` 排出每次 run 的成败序列（`o`=成功 `x`=失败）：

```text
run 296  oooooooooo             10 条  全过    88 条/小时
run 297  oooooooooo             10 条  全过    51 条/小时
run 298  ooooooooooooxxxxooooo  21 条  **第 13 条**起失败，4 条后自己恢复   33 条/小时
run 299  ooooooooooooxxxoooooo  21 条  **第 13 条**起失败，3 条后自己恢复   32 条/小时
run 300  ooooooooooooxxxoooooo  21 条  **第 13 条**起失败，3 条后自己恢复   （2026-08-22）
```

**run 300 是第三次复现，序列与 run 299 一字不差。** 三次了，不是巧合。

**确定的两件事：**

1. 两次超过 12 条的 run，**都恰好在第 13 条上开始失败**，形态一致 ——
   连续若干条卡满超时上限（129 秒整），然后**自行恢复**。就是 §1 那个「静默阻塞」。
2. **它会自己恢复**：run 299 在 3 条失败之后又连续成功了 6 条。
   所以**不是一个到点就锁死的硬配额**。

**⚠️ 不确定的（别当成结论）：**

- **不知道它按什么记账。** 一度以为「按对话条数，不是速率」，
  **那个推论是错的**：run 298 与 299 的千问请求速率几乎相同
  （32.7 vs 32.0 条/小时，间隔均值 114s vs 116s）——
  run 298 的千问 job 中间夹着卡满 130 秒的 DeepSeek 失败，**等于替我们做了打散**。
  **也就是说，「降速有没有用」这个变量至今没被真正测过。**
  （中位数确实从 53s 变成 108s，但均值和速率没变，标准差反而从 86 降到 34。）
- **不知道计数怎么归零。** run 299 比 298 晚 4 天、用同一个持久 profile，
  如果计数只增不减，它该在第 1 条就失败 —— 而它照样跑了 12 条。
  时间衰减？按天？按浏览器会话？**没测过。**

**要定性它，需要一次只动一个变量的对照**：同样 21 条，把速率显著拉低
（比如 10 条/小时），看第 13 条那道坎动不动。在那之前，
「换 profile 就能解决」只是一个**尚未验证的假设**，
虽然它和 §2.1 那条匿名态实测（约 5 个对话、换 profile 清零）方向一致。

#### 引用在 SSE 里，DOM 里没有（2026-08-17 实测）

与 NDSS 2026 论文的观察一致：**引用完整下发但浏览器不渲染。**

```text
端点   POST https://chat2.qianwen.com/api/v2/chat     （SSE）
帧     data:{...,"data":{"messages":[{...}]}}
引用   messages[].mime_type == "bar/progress"
       meta_data.match_num          ← 来源数（= 页面「N 篇来源」）
       meta_data.list[] 每条：
         title / url / raw_url / name（站点）/ publish_time / summary / type=web_source
```

**比我们原本对 citations 的要求还多**（多了站点名、发布时间、摘要）。
**公开圈没有任何项目从 `qianwen.com` 抽出过引用** —— 这是本仓自测的。

三条**已排除的死路**，别再试：

1. **DOM 里没有引用链接。** `[class*="search-content-"]` 那块只有 favicon 图，
   三种点击方式都展不开，外链 0 条。
2. **favicon 反查不出来源。** `s2.zimgs.cn/ims?key=<base64>` 解出来是
   **图标自己在 CDN 上的路径**（`cdn.sm.cn/temp/....PNG`），不是被引用的网页。
3. **class 名全带 CSS Modules 哈希**（`search-content-iMifAk` / `text-content-W61W05`），
   只能用前缀 `[class*="search-content-"]`。

#### 联网是按 query 触发的，没有开关

枚举输入区**全部 24 个按钮**：`研究`/`代码`/`翻译`/`AI写作` 等都是技能模式
（带 `aria-pressed`），`快速` 是模型选择器，**没有任何一个是联网开关**。

```text
"2026年杭州有哪些新开的博物馆？"    → 7 篇来源   ✓ 联网
"2026年8月新能源汽车销量排名前五？"  → 10 篇来源  ✓ 联网
"国产运动鞋品牌有哪些值得买的？"     → 0 篇来源   ✗ 未联网（run 296 十条全无）
```

~~**时效性问题触发，品牌对比类问题不触发**~~ —— **2026-08-22 推翻**。

P2-37 上线后从 SSE 直接读 `match_num`，同一条品牌提问
（`国产运动鞋品牌有哪些值得买的？`）实测 **`match_num=6`，6 条相关引用**。

**run 300（2026-08-22，21 条品牌类提问）把这条坐实了：18 条有效样本
`search_used` 全是 `true`，一条 `false` 都没有。** 与 NDSS 论文测的千问
98% 触发率吻合。**联网是常态，不是例外。**

**当初那个「0 篇来源」很可能是看页面读的** —— 而本节上面就写着
「引用完整下发但浏览器不渲染」。**拿渲染结果判断有没有联网，正踩在这个坑上。**
现在有了流里的 `match_num`，这个判断第一次有了可靠依据。

## 3. 外部情报（经 Grok 三轮检索，2026-08-16 / 17）

> 下面每一条都注明了来源与时间。**标「没找到」的是真的搜过没找到**，不是省略。

### 3.1 已被独立印证的两条

1. **持久化 profile 是社区已验证做法** —— `doubao2api` 有 `DOUBAO_BROWSER_DATA`，
   目的写明「复用 `webid`/`device_id`/`msToken`，避免每次冷启动换指纹」。
2. **stealth 注入对豆包无效** —— `lza6/doubao-2api` 标配 Playwright stealth，
   仍中人机（#5）、签名超时（#7）；Linux.do 2026-05 用 Playwright MCP 的结论是
   「效果更不佳，而且慢」。**本仓「不做 stealth 注入」不只是洁癖，是它确实不管用。**

### 3.2 NDSS 2026 论文（唯一接近抓包对照表的公开材料）

*Characterizing the Implementation of Censorship Policies in Chinese LLM Services*
（密歇根大学，会期 2026-02，artifact：`censoredplanet/chinese-llm-blocking`）
**MITM 了真实网页版 SSE**：

| 平台 | 搜索标记 | 搜索触发率\* |
|---|---|---|
| DeepSeek | `type: search-index` | 15% |
| 豆包 | 论文未写事件名；`event_type` ∈ {2001,2002,2003,2010}，`2010=seed_intention` | 60% |
| 千问 | 不显式声明搜索目标 | 98% |
| Kimi | `event: search_plus` | 81% |

\* 他们用的是审查类敏感 query。

> **⚠️ 这里原本写着「不能外推到品牌问句（我们实测品牌问句触发率≈0）」——
> 那半句已于 2026-08-22 删除。** P2-37 从 SSE 直接读 `match_num` 之后，
> 品牌问句实测 `match_num=6`。
>
> **而论文那个 98% 恰恰佐证了新测量**：千问的搜索触发率本来就极高。
> 这让「行为变了」这个解释变得不太可能 —— 更像是**我们当初看错了**：
> 拿浏览器渲染出来的「N 篇来源」去判断有没有联网，
> 而同一份文档上面就写着「引用完整下发但浏览器不渲染」。
>
> **教训：用一个已知会瞒报的信号去做判断，得到的结论也会瞒报。**

仓库里**有 `.http` 真实抓包样本，没有解析代码**（`viewer.py` 只打印不解析）。
`search_status` 取值：`search_skipped` / `search_completed` / `search_service_inactive`。
论文关键句：**搜索阶段的引用有时在 SSE 里完整下发，浏览器不渲染** —— 我们已在千问上验证。

### 3.3 封禁的处置梯度

- **DeepSeek ToS**：功能限制 → 暂停 → 关闭 → **禁止重新注册**。
  同一设备/手机号/支付方式再开新号，协议上允许连坐。
- **豆包 / 千问**：**不封号，只让这个号失去采集价值** —— 经济效果等于封号。
- 我们遇到的 3 天禁言属于临时功能限制。

### 3.4 明确「没找到」的（都搜过）

- 「N 个号 × 每号每天 M 条」的可持续参数；任何 GEO 公司披露的账号损耗率或成本
- headed vs headless 的封号率对照实验（三家中文的、ChatGPT 的都没有）
- 真机农场 vs Playwright 的封号率数字
- 覆盖豆包/千问/DeepSeek 中文网页版、可商用授权的公开回答数据集
- 三家**网页版** SSE 的完整字段手册（除 NDSS 那几个字段名）
- 任何开源项目从 `qianwen.com` 抽出引用 title+URL
- 国内公开运营的、用户知情贡献 AI 对话记录的面板产品

### 3.5 同行到底怎么做的

**不是靠更好的指纹。** 公开可查的结构是三段式：

| 环节 | 做法 | 代表 |
|---|---|---|
| 需求侧（人在问什么） | 买/建**真人面板**或 clickstream | Profound Prompt Volumes（double-opt-in 面板）· Semrush/Datos · Evertune EverPanel（自称 2500 万美国网民） |
| 回答侧 | 工业级前台抓取**或** API | Ahrefs 公开承认用网页版 · Semrush 写明不用 LLM API · Peec 客服承认 scrape UI |
| 结果侧 | 自有站日志里的 AI 爬虫与引荐流量 | Profound Agent Analytics（接 CDN 日志）· Similarweb（已把 DeepSeek 做成独立 referral 源） |

**关键**：`Profound` 的对话面板**不包括中国大陆平台**；`SparkToro` 2026-03 明写
prompt topics **不是**直接从 clickstream 面板来的。
**中文三家是全球 GEO 工具的覆盖洼地** —— 这是窗口，也解释了为什么没有现成参数可抄。

⚠️ **面板路线的合规雷已经炸过**：2025-12～2026-03，OX Security / Microsoft Defender /
G DATA 连续披露仿冒 AI 侧边栏的 Chrome 插件从 ChatGPT 和 DeepSeek 抽对话，
安装量约 **90 万**。合法面板与恶意插件的技术形态几乎相同，差别只在同意流程与 PII 处理。

### 3.6 一条会改变口径的判断

> **登录态网页版也不是「真实用户看到的」** —— 有记忆、个性化、配额档位、模型路由。
> Otterly 自己承认与手动搜索不一致；Conductor（2026-01）更直接：
> 多数爬虫实际抓的是**未登录/降级模型**，反而更不像真实用户。

对照我们的实际：那个 DeepSeek 账号侧栏挂着 2025-12 至 2026-07 的几百条私人对话，
**回答已被这份历史个性化过**，现在还叠了风控降权。
**「客户要真实用户看到的东西」这个交付口径，我们目前其实也没做到。**
这不是技术细节，它决定方法论怎么写、报告怎么措辞。

## 4. 攻这个难题的方向（按杠杆排序）

### 4.1 行为层去规律化（最便宜，收益最直接）

**不是加指纹，是让使用模式像人。** 被盯上的不是量（我们每天才 10–20 条），
是**规律性**：固定时段、固定 7 个问题、固定 40 秒间隔。一个真人不会这样用。

- **提问词每次改写**（语义等价、措辞不同）。
  **同时是学术推荐做法** —— Martinez 综述（2026-07）要求「至少沿
  run / 改写 / 日期 / 引擎 4 个轴变化」。一箭双雕：降低画像收敛 + 提高统计效力
- **打散时段与间隔**，别每天固定轮次
- **千问改用匿名 + profile 轮换** —— 彻底不碰账号

### 4.2 把网页采集从「唯一真理」降级为「校准通道」

网页版做成**有损、有备份、有降级**的通道，而不是 SLA 100% 的主库。
Grok 三轮检索的核心结论：**自建 Playwright 网页版采集，2026 年没有公开证据
表明可以稳态经营；我们碰到的静默降权就是这个模式的稳态，不是事故。**

### 4.3 结果侧指标（零封号风险、完全合法）

AI 引荐流量（`deepseek.com` / 豆包 referrer 进客户站）+ AI 爬虫打站日志。
测的是**结果**（被引用后有没有人来）而不是**过程**（AI 原话）。
对「可见度运营」这门生意，往往比原话截图更接近价值。

### 4.4 明确不建议的

- **再加指纹预算** —— 检测耐久度排序是 API < 渲染 < TLS < **行为**，
  而我们输在行为层。开源项目 OneGlanse 走「真反指纹浏览器 + 自有号 + 住宅代理」
  最大保真路线，作者自己写运维负担大到**做不成云服务**。
- **靠账号轮换扩量** —— 轮换解决「被识别后换皮」，解决不了「同一行为分布被建模」。
  N 放大只会让画像更快收敛。**且公开市场没有任何可持续参数可抄。**
